# 固定地图数据（从 apk 解出）

> 2026-11-13 实测确认。这个游戏**没有实时生成的随机地图**：apk 里放了几张固定地图，
> 每开一局从中选一张，**连资源地的位置都固定到每一格**。

---

## 1. 数据在哪

游戏包名 `inland.jwm.twgame`。从模拟器导出 apk 后，地图数据在 Cocos 的 JsonAsset 里：

```
assets/assets/app/import/**/<uuid>.json   # cc.JsonAsset，明文 JSON
```

相关资源名：

| 资源 | 内容 |
|---|---|
| `maps_0` | 50×50 小图 |
| `maps_13` / `maps_14` / `maps_15` | 600×600 三张主地图 |
| `land` | 184 条：地块字典（资源类型/等级/产量） |
| `landAttr` | 67 条：血量/占地尺寸/消耗/掉落 |
| `decoration` | 150 条：装饰物字典 |
| `decorations_0/13/14/15` | 装饰物摆放（纯视觉） |

## 2. 地图数组的格式

`maps_14` = 一个长度 360000 的整数数组，**600×600 网格**，下标 = `y * 600 + x`：

```python
value = maps_14[y * 600 + x]     # 与游戏内坐标一致
```

主城实测坐标 `(243, 291)`，在那个位置能看到 5×3 的 `93` 区块（建筑占地）。

## 3. 值 → 地块含义（靠 `land` 表）

`maps_N` 里的每个数字都是 `land` 表的 `id`：

| type | 含义 | 例 |
|---|---|---|
| 3 | 粮食地 | 0,1,2,3,4,301 |
| 4 | 木材地 | 5,6,7,8,9,401 |
| 5 | 石头地 | 10,11,12,13,14,501 |
| 6 | 建筑占地 | 16, 93（93 = 主城） |
| 7 | 水面 | 69,70,71,631..662 |
| 8 | 地形装饰位 | 43..68 |
| 9 | 其他地形 | 72,81..87… |

**验证**：`maps_14` 的 137 种值全部命中 `land.id`，36 万格零遗漏；
600×600 地图的四角都是 `71`（海），交叉印证「71 = 水」。

每格可读出：资源类型、等级（`lv`）、粮/木/石三项产量（`cereal`/`timber`/`stone`）、
可否占领（`occupy`），配合 `landAttr` 还有血量、占地尺寸（`1x1`/`2x2`）、
消耗体力、屯田时间、掉落。

## 4. 装饰物是什么

`decorations_14` 有 93530 条，格式 `[起点索引, 装饰id, 终点索引]`：

```
[5900, 94, 5901]   → 从第 5900 格到第 5901 格画「lake_109」（湖）
```

类型分布：阴影 50303、湖泊 14128、草丛 12662、小丘 10805、山体 5632。

**纯视觉美化，不影响资源/等级/归属，脚本决策用不到。**
所以默认不导出（`data/maps/decorations_*.json` 已在 `.gitignore` 里）。

## 5. 怎么重新导出

```bash
# 从模拟器取 apk
adb -s emulator-5554 shell "pm path inland.jwm.twgame"
adb -s emulator-5554 pull "/data/app/.../base.apk" apk/jiuwanmu.apk

# 导出地图（默认不含装饰物）
python -m jwm.apkmap apk/jiuwanmu.apk data/maps

# 需要装饰物时
python -m jwm.apkmap apk/jiuwanmu.apk data/maps --with-decorations
```

## 6. 识别「本局用的是哪张图」

`jwm/mapmatch.py` 提供匹配算法：给定若干「已知坐标 + 该格是什么」的样本，
对每张候选地图算一致率，取最高且领先足够多的那张。

自检结果（用 maps_14 自己的资源样本）：

```
maps_14  60/60 = 100.0%    ← 命中
maps_13  12/60 =  20.0%
maps_15  10/60 =  16.7%
```

区分力是压倒性的（领先 80 个百分点），不会误判。

### 还没解决的部分

算法本身验证过了，但**从游戏截图拿到可靠样本**这一步还没跑通：

- 水/陆签名：主城周边全是陆地，三张图都是 100%，无法区分（需要视野里有海）
- 资源类型签名：截图 OCR 的匹配分只有 0.65~0.78，够不到 0.80 阈值
- 锚点：屏幕主城位置和游戏坐标的换算还没对齐准

### 2026-11-13 晚：改走「apk 固定地图 + 网页全图视图」

不再从截图反推地形，直接把 apk 里的整张地图渲染到网页上看。已落地：

- `jwm/fixedmap.py` 负责渲染与单格查询，`jwm/fixedsrv.py` 负责给网页供图，
  `jwm/route_map.py` 加了 `fixed` / `fixedimg/` / `fixedtile` / `fixedguess` 四个接口。
- 网页上「全图 · 固定地图」和「实时视野 · 截图拼接」两个视图可切换，默认固定地图。
- 全图视图上叠了「已确认占领」和「开荒路线」，跟着 `/state` 实时重绘。
- 选图结果记在 localStorage，下次打开还是那张。

**资源地是零散的 1 格，不是成片的。** 实测 maps_14 的连通块：

| 类别 | 总格数 | 块数 | 最大块 |
|---|---|---|---|
| 粮地 | 48,703 | 33,097 | 14 |
| 木地 | 48,726 | 33,047 | 18 |
| 石地 | 48,607 | 32,886 | 14 |
| 建筑 | 14,018 | 814 | 586 |

三类资源格数量几乎相等、最大块不到 20 格，而建筑是成片的 —— 所以
「游戏里的森林/粮田」是装饰层画出来的观感，地图数据里每格只是独立的资源地块。
渲染出来是密集小点，不是大片色块，这是对的，不是渲染错了。

**地图行序还没实测确认。** 游戏坐标 y 向上（`world()` 里是 `home.y - y`），
而 `maps_N` 的行序到底是屏幕行还是游戏 y，apk 里没写。两种都渲染了一次，
网页上留了「上下翻转」开关，勾一下对照主城周边地形就能定，选完会记住。
**待办：真机对照一次，定下来之后就可以把开关去掉。**

**认图用的是「主城建筑密度」这个启发式。** 主城周围必有一片建筑（land.type=6），
拿真实主城坐标到每张候选图上数建筑格，只有「≥10 格且领先第二 3 倍」才给结论，
否则如实说不确定、让用户自己选。实测本局：

```
maps_14  15 格  ← 命中
maps_15   3 格
maps_13   0 格
```

这是启发式，不是证明。换局到别的地图如果主城周围本来就没有建筑，它会拒绝下结论。

**还没做：装饰层（湖/山/草）没有渲染。** 游戏画面里的湖泊来自 `decorations_14`
（lake 类 20 个 id），不影响资源，但少了它地图观感和游戏对不上，对照方向时会更费劲。


## 7. 这个方案的价值

| | 截图识别 | apk 固定地图 |
|---|---|---|
| 每格资源类型 | 只能认「这是树」 | 精确到木材地 Lv4 |
| 产量/血量/掉落 | 认不出 | 全部已知 |
| 覆盖率 | 只有当前视野 | 全图 36 万格 |
| 稳定性 | 受光照/弹窗/缩放影响 | 恒定 |

已知限制：apk 给的是「这张图固有地形」，谁占了哪一格、玩家自建的东西
仍要靠实时识别补 —— 但工作量从「认全部 36 万格」降到「只追踪变化」。
